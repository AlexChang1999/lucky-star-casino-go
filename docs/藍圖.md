> **定位**：把現有的 `Lucky_Star_Casino`（Java 21 / Spring Boot 3.3.5，7 個微服務）
> 全面重構為 Go，並在重構過程中補上 104 台中地區 9 個 Golang 職缺所要求的能力。
> **整理日期**：2026-07-31（v2，重新架構自「職缺需求彙整」版本）
>
> ✅ **本檔已於 2026-08-01 從 `lucky-star-notify-go` 搬進本 repo**，
> 是本專案的**單一真相來源**。原檔頭那句「這份文件描述的是下一個專案」到此失效。
>
> ⚠️ **§3.2 的資料層已被 `docs/ADR-001` 取代**：定案是
> **MySQL 寫入主庫 + MongoDB CQRS 讀端**，PostgreSQL 不採用。
> 下面 §3.2 的表格保留原始評估內容並就地標註，**不要照舊表施工**——
> 保留而不刪除，是因為「當初怎麼想、後來為什麼改」本身就是這個專案的敘事。

> ⚠️ **與 `CLAUDE.md` §2 的關係**：前身專案那條「沒有兩個實作就不要有 interface、

> DI 在那裡是對的。**兩者不衝突，是適用規模不同**——這個判斷力本身就是面試會考的東西。
> 本 repo 的 `CLAUDE.md` §2 已經照這個規模重寫過。

## 0. 這份文件是什麼／不是什麼

| 是 | 不是 |
|---|---|
| 取捨**之後**的施工藍圖，每個選型都有做或不做的理由 | 職缺關鍵字的購物清單 |
| 以現有 Java 專案的**真實架構**為基準 | 憑空設計的理想系統 |
| 把職缺要求當**驗收標準** | 把職缺要求當**待辦清單** |

**原則**：能講出「為什麼**不**用某個技術」比「用過某個技術」更值錢。
履歷上多一個 Elasticsearch，面試被問「你的資料量為什麼需要它」答不出來，是負分。

## 2. 取捨原則（後面所有決定都從這四條推出）

1. **難度價值密度優先**：先重寫「有難點」的服務。CRUD 服務重寫第二個，
   證明不了比第一個更多。
2. **每個技術都要能回答「為什麼需要」**：資料量、QPS、延遲要求說得出口才引入。
3. **正確性 > 關鍵字覆蓋**：帳務服務不為了用某個框架而犧牲可驗證性。
4. **能證明等價才算完成**：沿用 notify-go 的黑箱契約測試模式，
   同一份測試對 Java 版與 Go 版都要綠。**這是整個重構的安全網**。

## 3. 技術選型取捨表 ★ 核心決策

職缺清單 → 逐項表態。**「不做」的理由比「做」更重要**。

### 3.1 語言與框架

| 項目 | 決定 | 理由 |
|---|---|---|
| Go 1.25+ | ✅ **做** | 職缺共同要求；notify-go 已驗證 |
| **Gin**（業務服務） | ✅ **做** | 9 個職缺提及最多。CRUD 服務用它，生態與招募現實對齊 |
| **標準庫 `net/http`**（notify） | ✅ **保持** | notify-go 已用標準庫自幹 STOMP，**那是賣點，不要為了統一而改** |
| gRPC + Protobuf | ✅ **做** | 服務間通訊主力。Go 的主場，職缺明確要求。取代現有的服務間 REST |
| Echo / Fiber | ❌ **不做** | Gin 已覆蓋同一格能力，多學一個框架換不到任何東西 |

> **刻意不統一 HTTP 層**：業務服務用 Gin、推播服務用標準庫。
> 面試被問到時的答案是「框架解決的是路由與中介層的重複勞動，
> 而 STOMP over WebSocket 沒有現成實作，框架幫不上忙反而擋路」——
> **知道何時該用框架、何時該自幹，比全用框架更能展現判斷力**。

### 3.2 資料層 ★ 最需要取捨的一節

> ⚠️ **本節已被 `docs/ADR-001` 取代。**下表是 2026-07-31 的原始評估，
> **保留供對照，不要照它施工**。定案見表格下方的「現行定案」。

| 項目 | 原始評估 | 理由 |
|---|---|---|
| ~~PostgreSQL（帳務）~~ | ❌ **已改為不採用** | 原評估是沿用團隊分配。改用 MySQL 的理由見 ADR-001：團隊否決單一 MySQL 的技術依據（`SKIP LOCKED` 支援弱）在 MySQL 8.0 起就不成立 |
| ~~MySQL（CQRS 讀端）~~ | 🔄 **角色改變** | 從「讀端」改為**寫入主庫** |
| **GORM** | ✅ **做（主選）** | 職缺點名最多，且是**指定要學的新技術**。全服務主力 ORM |
| ~~`pgx` + 手寫 SQL~~ | 🔄 **改為 `database/sql` + MySQL driver** | 同上，PG 不採用後 `pgx` 自然失效。備案定位不變：只在 GORM 表達不了時局部降下去 |
| Redis | ✅ **做** | 分散式鎖、ZSET 排行榜、原子計數。沿用現有用途 |
| **MongoDB** | 🔄 **角色升級** | 原本是「學習目的」，現在是 **CQRS 讀端**（真實架構角色，見下） |
| **Elasticsearch** | 🔶 **延後** | 注單查詢在幾十萬筆的量級用索引完勝。**除非**要展示 ELK 日誌鏈路，否則不引入。真要做，放在最後一個 Phase |
| Memcached | ❌ **不做** | Redis 完全覆蓋 |

**現行定案（`docs/ADR-001`）**：

| 角色 | 選型 |
|---|---|
| 帳務寫入主庫（唯一真相） | **MySQL 8.4** |
| CQRS 讀端（Kafka 事件投影，可重建） | **MongoDB 8.0** |
| 分散式鎖 / ZSET / session（**主儲存**） | **Redis 7** |

金額一律 `DECIMAL(19,4)` 或整數最小單位，**嚴禁 float**——這條與選型無關。

> ⭐ **GORM 為主，但帳務的關鍵路徑要「看得見 SQL」**：
> 帳務正確性建立在兩件事上——「冪等鍵 UNIQUE 衝突」與「樂觀鎖 version 比對後的
> **受影響列數**」。GORM **做得到**（`clause.OnConflict`、`Where("version = ?")`
> 之後檢查 `RowsAffected`），問題只在它預設把產生的 SQL 藏起來，
> 而那正是最容易出錯的地方。
> **做法**：全專案用 GORM，帳務服務開 `db.Debug()` 或自訂 logger 把 SQL 印出來，
> 並對那幾條路徑寫「斷言 `RowsAffected == 1`」的測試。真的遇到 GORM 表達不了的
> 語句再局部降到 `database/sql` + 手寫 SQL。
> 面試時這是好答案：不是「我不敢用 ORM」，而是**「我知道 ORM 在哪裡會騙我」**。

> ⭐ **MongoDB 的定位（已於 2026-08-01 升級，見 `docs/ADR-001`）**：
>
> **原本的定位**是「為學習而保留」——照團隊 **ADR-010「明知規模不需要，
> 仍保留 Kafka 與 Redis」** 的模式，誠實寫下「以本專案的資料量，
> PG 的 `JSONB` 足以勝任，保留 MongoDB 是為了掌握文件庫的建模與查詢」。
>
> **現在不需要那個免責聲明了。** MongoDB 成為 **CQRS 讀端**之後有了真實的
> 架構角色：讀模型是**反正規化的查詢結果**——一筆玩家儀表板資料在關聯式讀庫
> 要 join 五張表，在文件庫就是一份文件一次讀出。這是文件庫在 CQRS 讀端的
> 標準理由，不是「因為想用 NoSQL」。
>
> 面試官問「為什麼用 MongoDB」時，答案從「為了學」變成
> 「讀模型天生是文件」。⚠️ 但 ADR-010 那個**「敢把為學習而保留寫進 ADR」
> 的模式仍然值得學**——只是這一項用不到了。

### 3.5 區塊鏈 ★ 取捨最大的一節

原 Java 專案是**模擬幣、無真實金流**。這一整塊是**新增**，不是重構。

| 項目 | 決定 | 理由 |
|---|---|---|
| **鏈上入帳監聽**（Block Scanner） | ✅ **做（測試網）** | 這是唯一真正有技術含量的部分：**確認數策略 + Reorg 處理 + 冪等入帳**，正好接上你已經在做的帳務正確性 |
| 第三方 RPC（Infura/Alchemy 等） | ✅ **做** | 測試網 + 託管 RPC |
| **自建節點** | ❌ **不做** | 同步一條鏈要幾百 GB 與數天，對作品集的**邊際價值近乎零**，維運成本卻是實打實的 |
| 地址派生（HD Wallet） | ✅ **做（測試網）** | BIP-32/44 派生是密碼學能力的具體展示 |
| **冷熱錢包分離／多簽／提幣審核** | ❌ **不做** | 這些要碰**真實私鑰管理**。作品集專案不該有任何「看起來能管真錢」的東西——寫得再好也只會讓人擔心，而不是加分 |
| 幣價匯率服務 | 🔶 **延後** | 接一個公開 API 即可，技術含量低 |

> **這一節的原則**：只做「能在測試網上跑、且核心難點真實存在」的部分。
> Reorg 處理與確認數策略是真難點；私鑰託管是**責任**不是**能力展示**。

## 4. 重寫順序 ★ 核心決策

**排序依據是「難度價值密度」，不是依賴關係**——契約測試讓任一服務都能獨立替換。

| # | 服務 | 為什麼是這個順序 | 覆蓋的職缺要求 |
|---|---|---|---|
| ✅ | `notification` | 已完成。自幹 STOMP = 最高價值密度 | WebSocket、長連線、心跳、併發 |
| **1** | **`wallet`** | ⭐ **最該做的第二個**。142 檔最大，且難點真實：冪等鍵、樂觀鎖、雙資料源、Outbox。直接對應職缺「帳務與交易正確性」與 Senior 的「分散式一致性」 | 帳務正確性、分散式交易、多 DB、鎖 |
| **2** | **`gateway`** | 只有 21 檔但**價值極高**：Go 寫 API Gateway（JWT、限流、熔斷、路由）取代 Kong。投入產出比最好的一個 | 限流熔斷、API 治理、資安 |
| **3** | **`game`** | RNG / Provably Fair / RTP band 有數學含量，且是娛樂城核心。Strategy Pattern 的天然舞台 | 高併發、設計模式、遊戲後端 |
| **4** | **`member`** | OAuth 三家整合。**且 Go 版能修掉 Java 版的單副本限制**（見 §5） | OAuth、JWT、2FA、水平擴展 |
| **5** | `rank` | Redis ZSET，相對直接。適合當「喘息」的一輪 | Redis 進階、排行榜 |
| **6** | `admin` | 97 檔但以 CRUD 為主，**價值密度最低**，放最後 | 後台、報表 |
| **7** | 區塊鏈模組 | 全新增。等帳務底子（wallet）穩了才接得上去 | 區塊鏈、密碼學 |
| **8** | K8s + OTel 全鏈路 | 服務齊了才有「跨服務追蹤」可追 | K8s、可觀測性 |

## 5. 「重寫比原版好」清單 ★ 面試爆點

**逐檔翻譯沒有故事，修掉原版的架構缺陷才有。**
以下每一條都是 Java 版**真實存在**的限制（來源：團隊 repo 的 `AGENTS.md` 與 ADR）：

| # | Java 版的限制 | Go 版怎麼做得更好 |
|---|---|---|
| 1 | `member-service` 的 session 存在 **JVM 記憶體**（OAuth 握手需要），因此**只能單副本**，重啟會讓進行中的登入流程全部失效 | session 移到 **Redis**，服務變回無狀態、可水平擴展。這是**原版明文承認但沒解**的問題 |
| 2 | `notification` **多副本的連線路由未解**（ADR-001 列為未來工作）——玩家連在 A 副本，事件卻進了 B 副本 | Redis Pub/Sub 或一致性雜湊路由。notify-go 的 ADR-001 已經記下這個問題，正好接著解 |
| 3 | JWT 驗證**沒有檢查 `type` claim** → member 發的 **refresh token 也能拿來開 WebSocket 連線** | 加上 `type` 檢查。⚠️ 注意：notify-go 目前**刻意保持與 Java 一致**以通過契約測試，**兩版要一起改** |
| 4 | Micrometer 的 gauge 回呼在**每次 scrape 時同步執行**，回呼裡下 SQL＝每 5 秒打一次 DB | Go 用 `atomic` + 背景刷新，gauge 只讀記憶體。notify-go 已是這個模式 |
| 5 | 7 個 JVM 各 `mem_limit: 1280m` + `-Xmx1g`，合計 **8.96 GB** 才跑得動 | notify-go 實測**閒置 12.9 MiB**／映像 18.6 MB。7 個服務全 Go 化後的資源對照，是這個專案最直觀的數字 |
| 6 | 服務間通訊是 REST | 換 gRPC，附上延遲對照數字 |
| 7 | `wallet.credit` 的唯一鍵衝突路徑（`WalletService:220-233`）**回不了正常值**——PG 的約束違反讓交易 aborted，catch 裡的回查自己也會炸，對外是 500 | Go 版同交易內補償回沖後回**贏家**的結果（`idempotent=true`）。⚠️ 這條**契約測試不涵蓋**（黑箱無法穩定重現該競態），由 `TestCreditDupEntryDoesNotDoubleCredit` 釘住 |
| 8 | `credit` 沒做過 T-090 B2 改寫，仍是讀改寫 + 樂觀鎖：**20 筆同玩家併發只有 1 筆成功**，其餘 409（實測，PG 的 EPQ 行為相同） | **尚未做，刻意的**——壓成條件 UPDATE 會讓 409 這個對外行為消失。要做必須先讓契約測試涵蓋它。理由見 `docs/ADR-002` 決策 7a |
| 9 | **壞 JSON 會回 500**。`GlobalExceptionHandler` 沒有處理 `HttpMessageNotReadableException`，但它註冊了 `@ExceptionHandler(Exception.class)`——於是 `ExceptionHandlerExceptionResolver` 搶在 Spring 內建的 `DefaultHandlerExceptionResolver`（那個才回 400）之前接住它 | Go 版回 **400**「呼叫端送了壞 JSON，伺服器不該說自己壞了」。✅ **2026-08-02 已對跑起來的 Java 實例複驗**（`TestMalformedJSON`，對 java 目標斷言 500 並通過）——當初的原始碼推導是對的 |
| 10a | **outbox poller 沒有鎖，多副本會重複投遞同一批**。`WalletOutboxPoller` 的 javadoc 自己寫著「本實作未對撈出的列加鎖……production 多副本部署時應改用 `SELECT ... FOR UPDATE SKIP LOCKED` 或 ShedLock」，因為它建立在單副本假設上 | Go 版直接用 `FOR UPDATE SKIP LOCKED`：第二個副本**不等鎖**（不會把投遞序列化）也**不拿同一批**（不會重複投遞），而是去撈下一批。⚠️ 代價是那筆交易必須明寫 READ COMMITTED，否則 gap lock 會擋住帳務的 outbox INSERT（地雷 #37）。由 `TestPublishPendingSkipsLockedRows` 釘住 |
| 10b | **清理排程是一句無界的 bulk DELETE**。壓測跑滿一週後保留期外可能是數百萬列，一次刪光會在帳務主庫上開一筆超大交易 | Go 版分塊刪（每塊 1000 列各自是一筆短交易），中途失敗只是「少刪幾塊」。清理本來就是延一天做也無害的維運工作。由 `TestPurgeSentOutboxDeletesBeyondOneChunk` 釘住 |
| 10 | **`playerId: 0` 或負數會回 404**。`DebitRequest.playerId` 只有 `@NotNull` 沒有 `@Positive`，於是非法 ID 一路走到「查不到錢包」 | Go 版回 **400**（`domain.ErrPlayerIDRequired`）。非正整數的玩家 ID 不可能有錢包，「請求有問題」比「資源不存在」準確。⚠️ 影響面為零：真實呼叫端送的都是真的 ID。✅ **2026-08-02 已對跑起來的 Java 實例複驗**（`TestZeroPlayerID`，對 java 目標斷言 404 並通過） |

> 第 5 條會是整份履歷最有說服力的一張圖：**同樣的 7 個服務，記憶體從 GB 級掉到 MB 級**。
> 前提是照 `AGENTS.md` §2.7 的規矩——**每個數字都要有實測輸出，同機施壓要標明**。

> ⭐ **ADR-000 是整個重構最好的敘事開場**。
> 當初團隊**正式決定過**「用 Java 而不是 Go」，並寫下理由。
> 新專案的第一份 ADR 應該是 **「為什麼現在改用 Go」**，
> 逐條回應當初那些理由：**哪些依然成立、哪些因為情境改變而不再成立、

### 6.2 32 條地雷的分類

**A. 仍然適用（業務與架構本質，語言無關）—— 必須全部帶走**

這一類是重構時**最容易漏**的，因為它們看起來像「Java 專案的事」，其實不是：

| # | 地雷 | 為什麼 Go 版一樣會踩 |
|---|---|---|
| 5 | wallet 是雙資料源 | Go **沒有** Spring 的 `@Transactional` 魔法，跨庫要顯式拆開，更容易錯 |
| 6 | `wallet.credit` 是事件、`wallet.credit.request` 才是指令 | 搞反會造成**無限迴圈**（listener 又觸發自己） |
| 7 | 改 Kafka topic 要同步改 infra 測試 | 同樣的同步要求 |
| 8 | 帳務＝冪等 + 防超扣 | 核心中的核心 |
| 11 | `friend.relationship.updated` 是**完整清單**事件不是增量 | 事件語義，看錯就資料錯 |
| 14–16 | 前端 mock 鏡像後端、老虎機權重同步、捕魚模型 | 只要前端還在就適用 |
| 17 | 風控 RTP 門檻是 **per-game 且含本金口徑** | 口徑搞錯會造成假的風控告警 |
| 18 | wallet `sub_type` 新增要**四同步** | 同步範圍不變 |
| 19 | gateway 路由：**具體路徑必須排在 catch-all 之前** | Go 的 router 同樣有順序語義 |
| 20 | 禮品商城在 wallet 內，不是獨立服務 | 重構時最容易「順手拆出來」，別拆 |
| 21 | 後台 JWT 與玩家 JWT 是**兩套 secret** | 混用會讓 gateway 驗不了 admin token |
| 22 | game→wallet credit 失敗必須落補償單，**冪等鍵絕不可換** | 換了就會重複入帳 |
| 23 | wallet 事件走 **Transactional Outbox**，勿改回直接 send | 重構時很容易「簡化」掉它 |
| 24 | 消費端「非冪等累加」必須去重，冪等寫入**不可**去重 | 兩者搞反都會錯 |
| 26 | 舊 DB volume 缺 migration 會讓服務開機即死 | 與語言無關的維運坑 |
| 31 | Gateway 有**兩套獨立限流** + 熔斷，調參有固定順序 | Go 版自寫 gateway 要重現這個分層 |
| 32 | **Redis 不只是快取**：排行榜與捕魚 session 是主儲存，`down -v` 會砍掉 | 與語言無關 |

**B. 需要轉換成 Go 的對應物**

| 原地雷 | Go 版對應 |
|---|---|
| 30 `mem_limit` 與 `-Xmx` 必須成對 | → **`GOMEMLIMIT` 與容器上限成對**。notify-go 已驗證（100MiB / 128M） |
| 25 Micrometer gauge 回呼不可直接查 DB | → Go 的 prometheus collector **同理**：回呼在 scrape 時同步執行，要用 `atomic` + 背景刷新 |
| 3 測試一律用 H2 記憶體 DB | → Go 沒有 H2。需另訂策略（`testcontainers-go` vs. 對 repository 介面做假） |
| 12 壓測數字不可虛構、co-located 要標明 | → **已沿用**進 notify-go 的 `AGENTS.md` §2.7 |

**C. 隨 Java/Spring 消失**

`mvnw`（1）、Spring Boot 同名 `@Bean`（4）、H2 設定細節（3 的實作面）、
`ps1` BOM（27）、`docker compose` 要 `--build`（29，其實通用但無 Java 特性）。

### 6.3 新 repo 的 `AGENTS.md` 怎麼起頭

**不要從空白開始。** notify-go 的 `AGENTS.md` §6 已經做過一次
「逐條核對團隊 31 條地雷、結論是只有 3 條可轉移」的工作——
那是因為它**只拿了一個服務**（而且是最不涉及帳務與遊戲的那個）。

**全面重構的可轉移率會高得多**：光是上面 A 類就有 **17 條**要原封不動帶走。
新 repo 的 `AGENTS.md` §2 應該以那 17 條為起點，
再加上 notify-go 自己累積的 28 條裡與併發/STOMP 無關的通則。

## 7. 路線圖與誠實的時間估計

以 notify-service（17 檔、3 天、含學習 Go）為基準外推，**兼職開發**：

| Phase | 內容 | 估計 |
|---|---|---|
| A | `wallet` 重構 + 契約測試 | 3–4 週 |
| B | `gateway`（Go 自寫，含限流熔斷） | 1–2 週 |
| C | `game`（RNG / RTP / 三款玩法） | 4–5 週 |
| D | `member`（OAuth ×3 + Redis session） | 2–3 週 |
| E | `rank` | 1 週 |
| F | `admin` | 2–3 週 |
| G | 區塊鏈模組（測試網） | 2–3 週 |
| H | K8s + OTel 全鏈路 + 效能總報告 | 2–3 週 |
| | **合計** | **約 4–6 個月** |

⚠️ **這個估計是誠實的，不是勸退**。你已經決定要做，那就該知道代價。

**每個 Phase 的 DoD 一律是三件事**：契約測試對 Java/Go 兩邊都綠、
`go test -race` 全綠、效能對照有實測數字。

## 8. 每個服務的重寫要點（施工時展開）

- **`wallet`**：冪等鍵 UNIQUE + 樂觀鎖 version 必須逐條對齊，不可簡化。
  雙資料源在 Go 沒有 Spring 的 `@Transactional` 魔法，**跨庫操作要顯式拆開**——
  這反而讓「為什麼不能有跨庫交易」變得一目瞭然。Outbox 保留。
  📖 開工前先讀 `docs/notes/Java版-CQRS-與指令事件分離.md`：完整資料流、
  「為什麼不同步雙寫」的四個理由、以及 `wallet.credit` 混用事件與指令造成的
  無限迴圈事故。Outbox 還要記得配清理排程（**只刪 SENT**）。
- **`gateway`**：路由順序（**具體路徑必須在 catch-all 之前**）、JWT 白名單
  （`/api/v1/auth/` 必須在白名單內，否則 OAuth callback 整條死掉）。
- **`game`**：RTP band 測試不可刪只可重算。Provably Fair 的種子承諾流程要保持可驗證。
- **`member`**：OAuth callback **必須經 gateway**，`OAUTH_PUBLIC_BASE_URL` 指向 gateway 而非 member。
- **`rank`**：Redis 是**主儲存**不是快取，`down -v` 會連排行榜一起砍。
- **`admin`**：稽核日誌不可篡改是唯一的硬要求，其餘是 CRUD。
