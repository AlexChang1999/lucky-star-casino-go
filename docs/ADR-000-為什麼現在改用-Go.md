## 這份 ADR 是被原本那份要求的

團隊 ADR-000 的「後果與注意事項」第 4 點寫著：

> **此決策不否定 Go**
> 若未來出現極端高吞吐、低延遲的單一服務（如即時推播閘道），
> 可在該服務局部評估 Go，但需另開 ADR 說明。

而它 2026-07-10 的現況校驗說「這個但書**至今未觸發**」。

**它已經觸發了。** `notification-service` 正是那句話點名的「即時推播閘道」，
它的 Go 版 [`lucky-star-notify-go`](https://github.com/AlexChang1999/Lucky_Star_Notify_Go)
已經完成並實測過。本檔就是原 ADR 要求的那份說明，
只是範圍從「該服務」擴大到全部——理由如下。

---

## 逐條回應原決策的三個理由

原 ADR 的三個理由**當時都是對的**。這裡逐條檢查它們今天還成不成立。

### 理由 1：「Spring Boot 一站式整合，Go 要自行拼裝」

**部分依然成立，但代價被高估了。**

原文列的 Go 缺點是「DI、交易管理、ORM、Kafka 整合需自行拼裝多個函式庫」。
實測下來：

- **DI**：Go 不需要容器。依賴關係在 `main.go` 手動組起來，一眼看完。
  對 7 個服務的規模，這是**優點**——Spring 的 `@Autowired` 讓依賴關係
  散在註解裡，新人要靠 IDE 才找得到。
- **交易管理**：這是原文最實在的一條。但也正因為 Go 沒有 `@Transactional`，
  **跨資料源不可能有交易**這件事變得無法被忽略——而團隊 ADR-001 的現況校驗
  自己記錄了一個踩坑：`@Transactional` 的動態代理在**同一個 Bean 內部
  自我呼叫時完全失效**，且沒有任何錯誤訊息。
  **框架的魔法在它失效時，比沒有魔法更危險。**
- **ORM / Kafka**：GORM 與 `segmentio/kafka-go` 都成熟。前身專案的 Kafka 消費端
  已在實戰中跑過三個 topic。

**結論：這條理由的重量從「決定性」降為「要多寫一些樣板」。**

### 理由 2：「團隊能力是首要考量——成員多為學習中的後端工程師」

**前提已經消失。**

這是原決策**最強**的理由，而且當時完全正確：讓一個新手團隊把精力放在帳務正確性
而不是語言細節，是對的取捨。

但本專案的情境是**單人、作品集導向、且目標是轉進 Golang 職位**。
「中文教學資源豐富」在這裡不再是優點——**學習曲線陡本身就是這個專案的目的**。

⚠️ 這條要誠實：**這不是原決策判斷錯了，是我的處境變了。**
把情境改變說成「他們當初錯了」，是重寫者最容易犯的傲慢。

### 理由 3：「效能差距可由架構彌補，正確性不能妥協」

**優先順序判斷正確，但「可由架構彌補」這半句尚未被實測支持。**

原 ADR 自己的現況校驗（2026-07-10）記錄了 T-090 壓測：

| 併發 | P99 | 錯誤率 |
|---|---|---|
| 150 | 1,164 ms | 5xx 78.0% |
| 1,000 | 5,055 ms | 5xx 89.3% |
| 1,000（限流後） | 5,317 ms | 429 shed 65.3% |

**帳務 gate 全程 0 違規 PASS**——所以「正確性不能妥協」這個優先順序是對的，
這一點本專案完全繼承。

但效能 gate（P99 < 500ms、5xx = 0）**持續 FAIL**，且原文誠實記錄根因包含
單機資源上限。同一份校驗還記錄了另一筆技術債：七個服務的 Dockerfile
都是裸的 `java -jar`，**沒有 `-Xmx`、compose 也沒有 `mem_limit`**。

對照前身專案的實測（同一台機器、同樣的工作性質）：

| | Java 版 | Go 版 |
|---|---|---|
| 閒置記憶體 | 七個 JVM 各 1280m 配額，合計 **8.96 GB** | **12.9 MiB** |
| 映像大小 | 數百 MB（`eclipse-temurin:21-jre-jammy`） | **18.6 MB** |
| 啟動時間 | 秒級 | **230 ms** |
| 5,000 條長連線 | — | 全部連上、零丟包 |

**結論：這條理由當初是合理的預期，但一年後的實測顯示差距沒有被彌補。**

---

## 決策

**全體後端服務逐步重構為 Go**，順序見 `docs/藍圖.md` §4。

### 但這不是「Go 比 Java 好」

原決策在它的約束下是對的。**本決策改變的是約束，不是結論的對錯：**

| | 團隊專案（2026-05） | 本專案（2026-08） |
|---|---|---|
| 開發者 | 新手團隊、多人協作 | 單人 |
| 首要目標 | 交付一個正確的系統 | 展示能力 + 學習 Go |
| 既有實作 | 無（從零開始） | **有一份會跑的 Java 版當正確答案** |
| 風險承受度 | 低（帳務不能錯） | 高（沒有真實使用者） |

最後一列是關鍵：**從零寫 Go 與「照著一份會跑的實作寫 Go」是兩件不同難度的事。**
原決策擔心的「手寫樣板寫錯帳務」，在有契約測試當安全網時風險大幅下降。

---

## 後果與注意事項

1. **契約測試是這個決策成立的前提，不是附加品。**
   沒有「同一份測試對 Java 與 Go 兩邊都綠」，這個重構就只是重寫，
   而重寫沒有任何證據說明它等價。前身專案已驗證這條路可行（14/14 兩邊全綠）。

2. **不統一 HTTP 層。** 業務服務用 Gin、推播服務保持標準庫自幹 STOMP。
   知道何時該用框架、何時該自幹，比全用框架更能展現判斷力。

3. **原 ADR 的優先順序完全繼承**：正確性 > 效能。
   帳務 gate 若在 Go 版出現任何違規，該服務就退回 Java 版，不硬上。

4. **`-race` 是硬性要求。** Go 有競態偵測器而 Java 沒有等價工具——
   這是換語言換到的、原 ADR 沒有列入考量的一項能力。

5. **這份 ADR 會被打臉的情況**：如果 Go 版在帳務正確性上出現 Java 版沒有的
   失敗模式，那就證明原 ADR 的理由 1 被我低估了。**那也要照樣寫進來。**
