## 背景

Java 的 `GiftTransferService` 在**一筆 PostgreSQL 交易**裡寫兩筆分錄：送出方 `DEBIT/GIFT`、
接收方 `CREDIT/GIFT`。要嘛都成功、要嘛都回滾，沒有中間態。

Go 版 wallet 已經有兩條各自調校過的熱路徑：

- `Debit`：條件 UPDATE + READ COMMITTED（地雷 #34）。
- `Credit`：讀改寫 + 樂觀鎖 + 1062 同交易回沖（地雷 #35、#36）。

兩者都各自帶 outbox 事件、各自處理冪等鍵衝突。

## 決策

贈禮拆成**三個各自冪等的步驟**，中間用一張狀態單（`gift_transfers`）串起來：

```
PENDING ──debit──▶ DEBITED ──credit──▶ COMPLETED
   │                  │
   │ 扣款被拒           │ 入帳失敗滿 5 次，或接收方錢包不存在
   ▼                  ▼
（刪單）           REFUNDING ──refund──▶ REFUNDED
```

1. **先立單、再動錢**。行程死在任何一步，重啟後看 `status` 就知道下一步。
2. **三步的冪等鍵都由呼叫端那把鍵衍生且永遠不變**：`{key}:gift:debit` / `:gift:credit` /
   `:gift:refund`（地雷 #4）。80 + 12 ≤ 100，剛好塞進 `wallet_transactions.idempotency_key`。
3. **每個狀態轉移都是 `WHERE status = 舊狀態` 的條件 UPDATE**，`RowsAffected == 0` 代表別人
   （另一個請求、另一個副本的背景重試）已經先轉走了，呼叫端重讀後照新狀態繼續（地雷 #3）。
   所以狀態單這一層**沒有交易、沒有 `FOR UPDATE`**，也就不會踩到地雷 #37 的 gap lock。
4. **背景重試**（`RunGiftRetries`，每秒掃一次）把卡住的單推到終態。入帳最多 5 次、指數退避
   1s/2s/4s/8s；**扣款確認與退款沒有次數上限**（放棄等於錢憑空消失），退避上限 5 分鐘。

## 為什麼不沿用單一交易

| 考量 | 說明 |
|---|---|
| 重用既有熱路徑 | 單一交易要同時鎖兩個 `wallets` 列，要重新處理**鎖順序**（A 送 B 與 B 送 A 同時發生會死鎖），而 `Debit` / `Credit` 已經各自驗證過隔離級別與衝突行為 |
| 事件語義 | 兩筆分錄各自走既有的 outbox 路徑，下游看到的與一般 debit / credit 事件同形 |
| 面試材料 | 「跨資源沒有交易時怎麼保證不丟錢」是 Saga 的實際案例，且每一步都能指出冪等鍵在哪 |

**代價（必須知道）**：

- 贈禮有中間態。請求回傳時可能是 `DEBITED`（錢已離開送出方、尚未到帳），此時回 200 且
  `creditTransactionId` / `receiverBalanceAfter` 為 `null`，背景會做完；同鍵重送可拿到最新結果。
  Java 沒有這個中間態。
- 多一張表、多一個背景迴圈要維運。
- 退款成功後**不回補當日額度**（退款可能發生在隔天，回補會扣到隔天的計數）。
  效果是額度偏嚴、午夜自動歸零，與 Java 對「多計」的取捨相同。

## 已知限制

1. **退款與入帳之間有一個很窄的競態視窗**。入帳結果不明（commit 逾時）時**不會**退款，
   而是用同一把鍵無限重試（冪等命中就完成）；確定沒入帳的失敗（樂觀鎖衝突）用盡 5 次後才轉退款，
   且轉退款前會查 `:gift:credit` 流水是否已存在。但「檢查」不是「鎖」：檢查之後、退款之前，
   另一個已在途的入帳仍可能提交，結果是接收方與送出方都拿到錢。完全消除要把入帳與狀態單
   放進同一個 MySQL 交易（會回到 Java 的鎖順序問題）。目前接受這個視窗，並以日誌
   （`贈禮入帳放棄，改為退款給送出方`）供事後對帳。
2. **結果不明的入帳若是確定性故障會永遠重試**（錢留在 DEBITED），代價是送出方的錢卡住並持續打 Error 日誌；
   這是刻意偏向「不憑空造錢」。
   典型例子：`:gift:credit` 冪等鍵被不相干的流水占用（`errGiftKeyCollision`），或接收方餘額溢位 / 違反 CHECK。
   目前**沒有告警與人工處理工具**，要補的話是針對 `status='DEBITED'` 且 `attempts` 很大的列發告警。
3. 扣款結果不明後，若背景重試才得到「餘額不足」而刪單，**當日額度不會回補**（偏嚴到午夜歸零）。

## 與 Java 的刻意分歧（皆需對 Java 版契約測試複驗）

1. **冪等重送只回給原送出方**。Java 的 `buildIdempotentResponse` 不看呼叫者，任何人帶同一把鍵都能拿到
   原贈禮內容（含原送出方的餘額）。Go 版其他人一律 409「Idempotency key already used by another gift」。
   同一個送出方用同一把鍵改送別人或改金額，仍照 Java 回原本那一筆。
2. **新增兩個結果碼**（Java 單一交易不會有）：已退款 → 409
   「Gift could not be delivered and the amount was refunded」；鍵屬於別人 → 409（如上）。
3. **`NewGiftDebit` 是 `subTypeDirection` 表的唯一例外**：`GIFT` 在帳上是雙向的，但對外的
   `/internal/wallet/debit` 仍只收 `BET` / `SHOP_PURCHASE`，不能因為贈禮而漂移。
