# Subagent 設定與決策理由

本目錄定義三個 subagent。**這一份記的是「為什麼是這三個」**，
角色細節看各自的 `.md`。

---

## 三個角色

| 角色 | 職責 | 關鍵限制 | 為什麼需要它 |
|---|---|---|---|
| `go-reviewer` | 對照 `AGENTS.md` §2 的地雷清單審查 diff，優先看**帳務正確性**與**無聲失敗** | **唯讀**，白名單沒有 Edit/Write | 開 PR 進 `develop` 前的閘門 |
| `go-tester` | 表格驅動 Go 測試、`test/contract/` 跨語言契約測試、`test/load/` 壓測 | **只碰測試檔**，不改產品碼、不 commit | 契約測試是整個重構的安全網 |
| `java-reference` | 讀團隊 Java repo，回答「原本到底怎麼做」 | **對團隊 repo 唯讀**，一個位元組都不改 | 重寫專案最貴的錯誤是「發明一個看起來合理的行為」 |

---

## 為什麼是三個，不是六個也不是一個

### 為什麼比前身專案多一個

`lucky-star-notify-go` 只有 `go-reviewer` 與 `go-tester` 兩個，因為它重寫的是
**唯一一個沒有資料庫、沒有帳務**的服務——業務規則少到主執行緒自己讀就夠了。

本專案不一樣：業務規則散在 **555 個 `.java` 檔**裡，而且每一條都有一個
**已經存在的正確答案**。找答案是「在另一個 repo 裡大範圍搜尋、讀很多、
結論很短」的工作——雜訊大、token 花費高、產出小。

**這正是 subagent 唯一真正划算的形狀。** 所以加了 `java-reference`。

### 為什麼不再多

`AGENTS.md` §3 記著一個實測成本：subagent 會自己重讀 `AGENTS.md` + `CLAUDE.md`，
**每次冷啟動約 10k token**。

因此：
- **小改動、單檔修正、問問題 → 主執行緒直接做**，不要派。
- 只有**雜訊大、要來回試錯**的工作才值得派。

角色再細分（例如拆出 `wallet-specialist`、`kafka-specialist`）只會讓每次冷啟動
重複付同一筆閱讀成本，換不到任何額外能力——**它們讀的是同一份 `AGENTS.md`**。

### 團隊 repo 那 6 個角色為什麼沒有全部移植

前身專案已經核對過一次：那 6 個裡有 4 個是 Java/Spring/PixiJS 專屬，
且 `devops` 那份的「never touch `main`」與單人開發約定衝突。
本專案採用 `develop` 分支流程之後那條衝突消失了，但那 4 個角色的**內容**
依然是 Java 生態專屬的，沒有可移植的部分。

## 三條共通紀律

1. **地雷知識只維護在 `AGENTS.md` §2**。
   ⚠️ **不要把地雷內容複製進 agent 檔案**——兩份會漂移，然後你不知道該信哪一份。
   agent 檔案只能**指向**它。
2. **審查者不可以是作者**。`go-reviewer` 的白名單刻意沒有 Edit/Write；
   `go-tester` 刻意不能改產品碼。一個能改掉問題的審查者，
   等於沒有審查；一個能改產品碼讓測試變綠的測試者，等於沒有測試。
3. **英文思考、中文輸出**。三個 agent 內部一律用英文工作（推理、工具指令、
   回報給主執行緒），由**主執行緒**翻成繁體中文給使用者。
   理由是 `CLAUDE.md` §0 的規定對象是「給我看的輸出」，
   而 agent 的回報是給主執行緒看的中間產物。

---

## 改完要重開 session

Claude Code 只在 session 啟動時註冊 `.claude/agents/`。
**改完這裡的任何檔案，要重開 session 才會生效**——
不重開的話你會以為改動沒作用，然後去改別的地方。
